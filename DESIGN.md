# Design notes

## 1. Отмена устаревших запросов

При каждом вызове `search(query)` в `createCountrySearch` (`src/core/countrySearch.ts`) я сначала
вызываю `controller?.abort()` у предыдущего контроллера и только потом создаю новый. Это происходит на
каждое изменение инпута, а не только в момент, когда debounce реально выстрелил сетевым запросом — то
есть abort случается даже если предыдущий таймер debounce ещё не успел сработать.

Этот signal идёт в `fetch` внутри `searchCountries` (`src/core/searchCountries.ts`), где он ещё
объединяется с таймаутом через `AbortSignal.any([signal, AbortSignal.timeout(ms)])`. Если пришёл новый
ввод — старый `fetch` реально прерывается на уровне браузера (в Network будет `canceled`), а не просто
теряется где-то в цепочке промисов.

Почему не через флаг/timestamp ("рисовать только самый свежий из пришедших ответов"): это не решает
проблему, а прячет её. Запрос всё равно долетает до сервера, занимает соединение и трафик, его `.then`
всё равно выполняется — просто результат выкидывается. На экране будет всё правильно, но по факту вместо
одного отменённого и одного успешного запроса в Network будет пачка полностью выполненных — а задание
прямо требует проверить руками, что устаревшие запросы помечены как `canceled`/`aborted`, что с
фильтрацией постфактум просто не произойдёт.

Отдельно за это отвечает `classifyError` (`src/core/classifyError.ts`) — он отличает "я сам отменил"
(`AbortError`) от настоящей ошибки. В `countrySearch.ts` catch просто делает `return` при
`kind === 'aborted'`, без вызова `onStateChange` — отмена вообще не долетает до пользователя как ошибка.

Клик по пункту истории (бонус, `src/main.ts` → `selectFromHistory`) идёт в обход debounce через
`searchNow` — и тут всплыл реальный баг: `searchNow` сразу отменяет контроллер и вызывает поиск напрямую,
но debounce внутри себя всё ещё держит отдельный `setTimeout` на предыдущий ввод, который рано или поздно
выстрелит сам по себе с устаревшими аргументами. Решение — `debounce` (`src/core/debounce.ts`) теперь
возвращает функцию с методом `.cancel()`, и `searchNow` явно его вызывает перед прямым запуском поиска.

## 2. Задержка debounce — 400мс

Подобрано на ощущениях от печати, не вычислено формулой. Логика такая:

- **0мс (без debounce):** каждая буква — отдельный запрос. Даже с рабочей отменой это лишняя нагрузка на
  `countries.dev` и мигание `loading → canceled → loading` на экране при каждом нажатии.
- **слишком много (1-2 секунды):** человек закончил печатать, а результат появляется с заметной задержкой
  — ощущается как подвисание интерфейса, а не как нормальная сетевая задержка.

400мс заметно больше паузы между нажатиями при обычной печати (там обычно 100-200мс) и при этом не
воспринимается как лаг после того, как ввод закончился.

## 3. Сложность

- `mapCountryResponse` — O(L), где L — число языков у конкретной страны (обычно 1-4, не растёт с
  размером выдачи). На N стран в ответе — O(N·L), то есть линейно от объёма данных.
- `debounce` — O(1) на каждый вызов: один `clearTimeout` + один `setTimeout`.
- `createCountrySearch` — O(1) на каждый `search()` (один `abort()` + один новый `AbortController`),
  обработка результата — O(N) через `mapCountryResponse`.

**Бонус — кэш и дедупликация (`createCachingSearch.ts`):**

- Чтение/запись в кэш и в карту "в полёте" — O(1) амортизированно (обе на `Map`, ключ — нормализованная
  строка запроса).
- Если запрос уже в кэше или уже летит — O(1), реальный `fetch` не вызывается вообще.
- Память растёт линейно с количеством **уникальных** запросов за сессию — O(U). TTL/вытеснение
  (LRU и т.п.) не реализованы: для объёма "один человек ищет страны в рамках одной сессии" это не
  проблема, но для долгоживущего приложения это известный компромисс, не решённый в рамках задания.
- `addToHistory` (`src/core/searchHistory.ts`) — O(H), где H — длина истории, но она жёстко ограничена
  8 записями (`HISTORY_LIMIT`), так что на практике это O(1).

## 4. Чистый код

- **Разделение ответственности:** `debounce` занимается только таймером, `searchCountries` — только
  `fetch` и семантикой `response.ok`/404, `mapCountryResponse` — только преобразованием данных,
  `classifyError` — только классификацией ошибки. Друг про друга и про DOM они ничего не знают. Собирает
  всё это в состояние экрана один `createCountrySearch`.
- **DI для тестируемости:** `createCountrySearch` принимает `search` как зависимость
  (`CountrySearchDeps`), а не импортирует `searchCountries` напрямую. В тестах
  (`tests/countrySearch.test.ts`, `tests/countrySearch.race.test.ts`) туда подставляется фейковая
  функция с управляемым порядком резолва промисов и без реальной сети — именно так проверяется гонка.
- **Минимальные типы по факту использования:** `RawCountry`/`Country` (`src/core/types.ts`) содержат
  только то, что реально читается в коде. Поля `area`, `borders`, `currencies`, `flagEmoji` добавлялись
  по одному, каждое под свой падающий тест, когда реально понадобились для детального вида, а не выписаны
  все поля схемы `countries.dev` заранее "на будущее".
- **Без магических строк в UI:** `ErrorKind` (`src/core/classifyError.ts`) — закрытый union, текст для
  пользователя собирается в одном месте (`errorMessage` в `src/main.ts`), а не разбросан по коду.
- **Деградация вместо жёсткой зависимости:** `src/ui/flag.ts` сначала пробует картинку флага
  (`flags.svg`), и если она не загрузилась — подставляет emoji-флаг из того же ответа API
  (`flagEmoji`). Без этого один недогруженный сторонний CDN превращается в битую иконку на весь список.
- **Разделение "своей" отмены и "общего" запроса (бонус):** `createCachingSearch.ts` оборачивает каждый
  вызов в собственный промис, который реагирует только на сигнал конкретного вызывающего
  (`followCaller`), не трогая промис самого сетевого запроса. Если бы один `AbortController` был общим
  на все, отмена одним вызывающим (например, он передумал вводить то же самое) рушила бы результат для
  всех остальных, кто ждёт тот же кэшированный запрос — именно это явно запрещено условием бонуса.
